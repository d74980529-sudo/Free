## 0. ROLE AND OUTPUT RULES

You are a senior PHP engineer. Build a complete, production-ready, brand-new Free Fire likes shop for Bangladesh.

**Stack:** Pure PHP 8.2, MySQL 8, PDO prepared statements only, cURL, no Laravel, no Node, no Composer needed. Apache shared hosting (cPanel), `.htaccess` pretty URLs, timezone Asia/Dhaka. Bangla default, English toggle. Currency ৳.

**Hard boundaries (never break):**
- New brand. Do not copy the name, logo, or Telegram of any existing site. Reference flow only: Google login, wallet, UID likes, normal vs instant, delivery report.
- Delivery calls ONLY an HTTP provider the admin configures. No game exploits, guest-account tools, Frida hooks, token stealers, or direct Garena client.
- Ship no real API key, bot token, or OAuth secret. All secrets are blank in seed data and stored server-side only.
- Secrets never reach the browser, logs, or error pages.

**How to deliver:**
1. First print the file tree, then the DB schema (`install/schema.sql`), then code file by file in dependency order.
2. No placeholders like "TODO" or "implement later". Every listed feature works.
3. Every file is complete. Keep files under ~400 lines where practical (split controllers, services, views).
4. End with a self-test checklist mapped to the Acceptance section and a README.

If the host cannot place `/app` outside webroot, add `Require all denied` `.htaccess` in `/app`, `/storage`, `/cli`.

### 1.2 Conventions
- Front controller routes by a small router table. Controllers are thin, Services hold logic.
- All money is `DECIMAL(12,2)`. Compute in PHP with integer paisa (`(int) round($x*100)`) to avoid float errors. Display helper `taka()` hides `.00` on whole values.
- All times stored UTC-agnostic as `DATETIME` in Asia/Dhaka (set `date_default_timezone_set` and MySQL session `time_zone='+06:00'`). Display via one helper.
- Every state change writes a history row (orders, deposits) and a `staff_activity` row when done by staff.
- One `Logger` writes to `provider_logs`, `api_logs`, `storage/logs/app.log`. Redact keys, tokens, signatures, Authorization headers.
- Strings come from `/Lang/*.php` plus an admin-editable override table `translations` (key, bn, en) so the admin can fix labels without code.

## 4. AUTH — GOOGLE ONLY, NO REGISTER

No register page, no email/password signup, no "create account" form. Only the button "গুগল দিয়ে লগইন করুন" on a light login card with the logo.

**Admin → Login:** Client ID, Client Secret (stored encrypted with a key from `config.php`, shown masked), read-only redirect URL (`{site}/auth/google/callback`), toggle "Allow new Google users" (default ON), toggle "Remember me 30 days".

**Flow (Authorization Code):**
- Generate `state` (random, stored in session, single use) and `nonce`; verify state on callback. Use PKCE (S256).
- Exchange the code server-side with cURL. Verify the ID token: `iss` in (`https://accounts.google.com`, `accounts.google.com`), `aud` = client ID, `exp`, `nonce`, `email_verified = true`. Reject unverified emails.
- Match by `google_id` first, then by email. Same google_id or email never creates a second row; if matched by email, attach the google_id.
- ON: first success creates user (google_id, email, name, avatar, referral code, language) and lands on Home. OFF: only an email already in `users` may enter; others see "This Google account is not allowed".
- Banned users cannot enter; show the ban reason if the admin enabled it.
- Respect the blacklist (email, IP) at login.
- Session: `session_regenerate_id(true)` on login, cookie `HttpOnly; Secure; SameSite=Lax`, separate cookie name and storage from admin, idle timeout and absolute lifetime configurable, `user_sessions` row with IP, user-agent, last seen. Users can see and revoke their own sessions in Profile.
- Admin can still create users manually, ban, adjust balance, grant API access.

### 5.1 Order screen (`/order`)
Selected product card, then:

Success row: player name, region, current likes if returned, level if returned. Nickname saved on the order. Fail: "Player not found. Check the UID." and the input is NOT cleared. Changing UID or region clears a passed check. A signed server-side token (`check_token`: uid, region, nickname, expires in 10 min, HMAC) is stored in the session so Confirm can verify the check on the server, not only in the UI.
- Optional **coupon** field (order-type coupons), validated live, shows discount. Final price is always recomputed server-side.
- Optional **recent UIDs** (last 5 UIDs this user ordered), tap to fill.
- Price summary: price, rank discount, coupon, total, wallet balance, remaining balance. If balance is low, show "Add Money" shortcut with the exact shortfall.
- Package rules HTML under the form, collapsible.
- **Confirm** stays disabled until the check passes (when "Require name check" is ON) and the user is logged in (guests see "Login with Google").

**Seed rules (bn/en, editable):**
- Normal: one order per UID per cooldown; likes continue until complete; wrong UID no refund; no likes → open a ticket.
- Instant: starts immediately; a short first batch may finish next day; `likes_given = 0` → auto refund once; wrong UID no refund.

### 5.2 Server-side enforcement (PHP, not only UI)
Checks in this order, all returning clear bn/en errors with stable codes:
`MAINTENANCE`, `BANNED`, `BLACKLIST` (UID, email, phone, IP), `CSRF`, `RATE_LIMIT`, `PACKAGE_INACTIVE`, `RANK_LOCK`, `REGION_LOCK`, `UID_FORMAT`, `NAME_CHECK_REQUIRED`, `COOLDOWN` (per UID per package, also across packages if configured), `DAILY_CAP` (per UID and optional global per package), `MIN_MAX`, `COUPON_INVALID`, `INSUFFICIENT_BALANCE`, `DUPLICATE_SUBMIT`.

**Idempotency:** each confirm form carries a one-time `idempotency_key`; a repeat key returns the original order instead of creating another. Double-click safe.

### 5.3 Confirm transaction
1. `BEGIN`; `SELECT ... FOR UPDATE` the user row.
2. Re-check cooldown/cap with row locks.
3. Compute price from DB (product → rank override → coupon). Never trust browser values.
4. Insert `wallets_ledger` debit, update `users.balance` (and verify `balance >= 0`), insert order with a rules snapshot, insert `order_status_history`.
5. `COMMIT`.
6. **After commit**, if `api_mode=auto`, call the Like provider (do not hold a DB lock during HTTP). On provider success store provider order id and set status `processing`. On provider failure: status `failed_submit`, queue retry (max 3 via cron), failover to the next provider by priority, alert via Telegram. If all retries fail: auto refund (idempotent) and status `refunded`/`failed`. If `api_mode=manual`, status `manual_pending` for staff.
7. Success modal: "Order Successful! Your order has been placed successfully" and "View Order History".

### 5.4 Order status machine
`pending → processing → partial → completed`, plus `failed_submit`, `failed`, `refunded`, `partially_refunded`, `manual_pending`, `cancelled`. Only allowed transitions are accepted; each writes `order_status_history` (from, to, actor, note, time). Refund and credit code paths check state first so they can only run once.

### 5.5 Extra order features
- **Scheduled / repeat orders:** user can schedule the same UID again when cooldown ends (reminder only, never auto-charge without confirm; optional "auto re-order" with explicit opt-in and balance check).
- **Order notifications:** in-site notification center (bell) for completed, partial, refunded, deposit approved, ticket reply. Optional email via SMTP.
- **Receipt:** printable `/orders/{order_no}/receipt` (no PDF library; print CSS).
- **Share card:** simple "Likes delivered" image-free share text with copy button (no UID shown unless the user chooses).

### 7.2 Auto pay — Nagorik Pay
Follow https://nagorikpay.com/developers/docs (page dated 2026-09-04). Pure PHP cURL, timeouts 10s connect / 30s total, TLS verify on.

**Admin → Payment gateways → Nagorik Pay:** enabled, mode sandbox|live, `live_base_url` default `https://secure-pay.nagorikpay.com`, `sandbox_base_url` default `https://sandbox-api.nagorikpay.com`, brand API key (masked), optional webhook secret. Empty key hides the gateway. The docs also name live host `https://api.nagorikpay.com/`; base URLs stay editable, paths are fixed: `/api/payment/create` and `/api/payment/verify`. A `sk_test_` key is sent only to the sandbox host (block the call otherwise). Show the webhook URL (`{site}/pay/nagorik/webhook`) and a "Test connection" button.

**Create:** after the pending deposit row exists, `POST {base}/api/payment/create`, headers `Content-Type: application/json`, `API-KEY: {key}`. JSON: `cus_name, cus_email, amount` (no trailing `.00` on whole taka), `success_url, cancel_url, webhook_url, metadata {"deposit_id","user_id"}`. Success: `status true, message, payment_url` → redirect. UI: "Opening payment page", then "Payment processing... Waiting for gateway response". Error: `status false` plus message → do not credit, mark deposit `failed`, show the message.

**Return (success_url)** query (`transactionId, paymentMethod, paymentAmount, paymentFee, status`) is NOT proof. Always `POST {base}/api/payment/verify` with `{"transaction_id"}` and the same API-KEY. Credit only if verified status is `COMPLETED` AND verified amount equals the deposit amount. `transaction_id` is unique. Second credit is a no-op. While verification is pending, the return page polls `/wallet/deposit/{id}/status` every 3s up to 60s.

**Webhook** `POST /pay/nagorik/webhook`, form-urlencoded (not JSON). Fields: `paymentMethod, transactionId, method_transaction_id, paymentAmount, paymentFee, status = completed|pending|failed`. Headers: `X-NagorikPay-Timestamp`, `X-NagorikPay-Event`, `X-NagorikPay-Signature = sha256=<hex>`. Signed string = `timestamp + "." + raw body` (read `php://input`, not `$_POST`). Key = webhook secret if set, else brand API key. Compare with `hash_equals`. Reject timestamps older than 300 seconds (also reject far-future). Reply HTTP 200 quickly (flush the response, then continue), then run the verify API. Credit once only on `COMPLETED`. `pending` and `failed` do not credit. `cancel_url` marks the invoice cancelled. Never trust a browser amount. Log every call (headers minus secrets, body, result) without the API key. Replay of the same `transactionId` is a logged no-op.

**Credit routine (shared by return, webhook, cron):** `BEGIN` → `SELECT deposit FOR UPDATE` → if status already `credited` return → verify rules → insert one ledger credit + update balance + set `credited` + store verified payload → `COMMIT` → notify.

## 12. SECURITY

- PDO with `ATTR_EMULATE_PREPARES=false`, prepared statements only, no string-built SQL (whitelist any dynamic ORDER BY column).
- CSRF token on every POST (and on state-changing AJAX via header), single-purpose tokens for destructive actions.
- Escape all output with a context-aware helper; admin-entered HTML only through the allowlist sanitizer.
- Security headers: CSP (self + needed hosts, no inline script except nonce), `X-Frame-Options: DENY`, `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy`, HSTS when HTTPS.
- Uploads: extension + MIME (finfo) + image decode check, random filenames, size limits, stored in `/uploads/*` with `.htaccess` `php_flag engine off` / `RemoveHandler` / `Require all denied` for script types. Never trust the client filename.
- Sessions: separate names and save paths for admin and user, `use_strict_mode`, regenerate on privilege change, secure cookie flags.
- Rate limits (DB or file based, by IP + user): login, check-name, order, deposit submit, reseller API, webhook (generous).
- Prices and credit amounts only from the database or from Nagorik verify. Idempotent credits and refunds (unique ledger refs + status guards).
- SSRF guard on admin-configured provider URLs: allow only http/https, block private/loopback/link-local ranges after DNS resolution, cap redirects (0–2), cap response size (1 MB), timeouts.
- Webhook signature as specified; constant-time comparisons everywhere.
- Error handling: production hides errors, logs them; user sees friendly message with a reference ID.
- Installer lock: after success write `install/.lock`, and refuse to run again.
- Password policy for admins, bcrypt/Argon2id, `password_needs_rehash`.

## 18. ACCEPTANCE

- Change primary to blue in Appearance and both shop and admin turn blue; preview matches; rollback restores.
- Replace the logo and it shows in header, login card, footer, and admin sidebar; removing it falls back to text.
- Add a slide with a link; the homepage slider opens that link. No active slide = no slider.
- A notice appears in the top bar and can be turned off; no gap remains.
- Pop-up respects frequency and shows at most one per page.
- A product card shows the admin price and opens the order form with that package; the charged price equals the DB price even if the browser is tampered with.
- Google login creates a user; there is no register form; OFF toggle blocks unknown emails; banned users are blocked.
- Check Name shows a player name or a clear error, the UID is not cleared on failure, and Confirm stays disabled (and is rejected server-side) until it passes when the rule is on.
- Double-click on Confirm creates one order and one debit.
- Cooldown, daily cap, blacklist, maintenance, and insufficient balance are all enforced via direct POST, not only the UI.
- Manual deposit sends a Telegram message, rejects duplicate TrxID, and credits only after approve, exactly once.
- Nagorik return does not credit until verify says COMPLETED for the same amount; a forged return URL credits nothing; a bad or stale webhook signature is rejected; a second webhook does not double credit.
- Expired unpaid auto invoices cancel by cron; manual pending deposits do not.
- My Orders lists only that user's orders with before/given/after.
- `likes_given = 0` refunds once, even if cron runs twice or admin also clicks refund.
- Reseller API: wrong key 401, over 60/min 429, disallowed IP 403, same rules as the site, every call logged.
- Provider failure retries up to 3 times, fails over, alerts Telegram, then refunds.
- Admin permissions: a Support user cannot open Appearance, Providers, or Backup by URL.
- No secret appears in HTML source, JS, logs, or error pages.
